# PLAN — CLI startup performance

Branch: `perf/cli-startup`

## Problem

`emb ps` takes ~1.7s. The command it wraps takes ~0.46s. Almost all of the
difference is JavaScript module loading that happens before any useful work.

Measured on `~/Work/klaro/klaro`, `@enspirit/emb@0.30.2` installed from npm
(medians over batches of 12–16 warm runs; machine variance is ~20%, so treat
deltas under ~150ms as noise):

| command | time |
| --- | --- |
| `docker ps` | 234 ms |
| `docker compose ps` | 457 ms |
| `emb --version` | 259 ms |
| **`emb ps`** | **~1670 ms** |

`docker compose ps` is the fair baseline — it is the call `emb ps` actually
makes. So emb adds **~1.2s of pure overhead**, a 3.7x multiplier.

Where it goes:

```
   99 ms  node boot (floor)
  160 ms  oclif bootstrap
  ~1050 ms  loading emb's module graph + config + monorepo init
  ~400 ms  docker compose ps subprocess + rendering
```

The CPU profile attributes 86% of the time to `compileSourceTextModule`,
`wrapSafe`, `internalModuleStat` and `readFileUtf8` — parsing and compiling
JavaScript, not running it. emb's own logic is fast: config load is 39ms,
monorepo init is 50ms, and both are already instrumented via `EMB_DEBUG_PERFS`.

The headline number (`npm run bench:modules`, klaro, manifest present):

| | modules compiled | source |
| --- | --- | --- |
| `emb --version` | 161 | 0.62 MB |
| **`emb ps`** | **2116** (841 cjs, 1275 esm) | **21.20 MB** |

`emb ps` compiles **21 MB of JavaScript** to shell out to `docker compose ps`.
The largest contributors, none of which it uses:

| package | files | source |
| --- | --- | --- |
| `@kubernetes/client-node` | 826 | **14.5 MB** |
| `@grpc/grpc-js` | 64 | 652 KB |
| `ssh2` | 20 | 592 KB |
| `protobufjs` | 35 | 293 KB |
| `lodash` (via `graphlib`) | 200 | 155 KB |

`@kubernetes/client-node` alone is **two thirds of everything `emb ps` parses**.

Startup cost is essentially **constant regardless of monorepo size**. klaro (77
tasks) versus `examples/fullstack-app` (2 components) differ by only ~36ms in
monorepo init. This is a fixed tax on every invocation.

## Root cause

Two independent mechanisms, both about *reachability* of imports.

### 1. Barrel imports weld the codebase into one unit

`src/index.ts` re-exports everything. 38 files import from it. The result is
that touching any part of the code pulls in all of it. Traced chain for `ps`:

```
cli/commands/ps.js
 → docker/index.js → docker/resources/index.js → DockerImageResource.js
   → monorepo/index.js                     (barrel)
     → monorepo/operations/index.js → tasks/RunTasksOperation.js
       → kubernetes/operations/index.js
         → @kubernetes/client-node → @grpc/grpc-js + protobufjs + ws
```

`RunTasksOperation` imports the Kubernetes operations statically but only uses
them inside one `case` branch. `graphlib` (+ `lodash`) arrives the same way, via
`monorepo/utils/graph.js`, for `findRunOrder` — which `ps` never calls.

### 2. Clients are constructed eagerly for every command

`BaseCommand.init()` runs `new Dockerode()` and `createKubernetesClient()` on
**every** invocation. `ps` uses neither; it shells out to `docker compose`.
`dockerode` is what drags in `ssh2` and `@grpc/grpc-js`, for transports we are
not using.

### Note on `oclif.manifest.json`

Without a manifest, oclif imports every command file at startup to read its
metadata — which, given the barrels above, means loading the entire codebase
just to print `--version`. The published package *does* ship a manifest
(`files` in `package.json`, generated by `prepack`), so this only ever affected
npm-linked local development, where it cost ~820ms on every command.

**This is already handled and is not part of this work.** It is documented here
only because it explains why earlier measurements against a linked checkout
looked different. Worth noting separately: adding `oclif manifest` to
`npm run build` would give local development the same behaviour as production,
at the cost of needing a rebuild after changing command metadata.

## Fixes

Ordered by value-to-risk. Each phase is independently shippable and independently
measurable.

### Phase 0 — Benchmark harness — DONE

- `npm run bench:startup [dir]` — wall-clock ladder, median of N batches.
- `npm run bench:modules -- <cmd> [--cwd dir]` — modules compiled and bytes
  parsed, grouped by package.

Everything below is verified with these. Without them we are guessing — the
machine has ~20% run-to-run variance and several plausible-sounding fixes turned
out to be worth nothing.

Two things the harness had to get right, both of which caught real mistakes:

- **It counts ESM as well as CJS.** An earlier `Module.prototype._compile`-only
  count reported 836 modules / 4.3 MB for `emb ps`. The true figure is 2116 /
  21.2 MB — the CJS hook was blind to `@kubernetes/client-node`, which is ESM
  and is *two thirds of the entire cost*. Counting one pipeline would have
  pointed this whole effort at the wrong targets. ESM is counted via a
  `module.register()` loader hook reporting over a `MessagePort`; results are
  deduplicated against the CJS hook, since a CommonJS file imported from ESM
  passes through both.

- **It warns when `oclif.manifest.json` is absent.** Without one, oclif loads
  every command module at startup, which inflates `emb --version` roughly 5x
  and makes local numbers describe a configuration no user runs.

Note `register()` must be called from a `node --import` preload, not
`--require`: during a CJS preload the ESM loader is not yet initialized and
`register()` fails with a misleading `Missing internal module` error.

### Phase 1 — Stop importing the root barrel for `getContext` — DONE

26 of the 38 files that imported from `@` needed only `getContext` (or
`getContext` + `setContext`, or `getContext` + the `EmbContext` type). All of
those live in `src/context.ts`, which has no runtime dependencies at all
(it imports types only; `types.js` compiles to `export {}`).

Mechanical rewrite:

```ts
- import { getContext } from '@';
+ import { getContext } from '@/context.js';
```

`AbstractOperation` also took a `import type { EmbContext } from '@/types.js'`,
making the erasure explicit. 12 root-barrel imports remain; they pull real
values (`Monorepo`, `ResourceInfo`, `CommandExecError`) and belong to Phase 5.

**Result: no change to module count (2116) or wall-clock — as expected.** The
graph stays fully connected until the last edge into each subtree is cut. What
this phase bought is structural, and it is visible in the trace: the route from
`ps` to Kubernetes used to run

```
ps.js → docker/index.js → docker/resources/index.js → DockerImageResource.js
      → monorepo/index.js → monorepo/operations/index.js
      → RunTasksOperation.js → kubernetes/operations/index.js → @kubernetes/client-node
```

and now runs

```
ps.js → cli/index.js → cli/abstract/index.js → BaseCommand.js
      → kubernetes/client.js → @kubernetes/client-node
```

That whole barrel route is severed. **A single edge — the eager
`createKubernetesClient()` import in `BaseCommand` — now stands between `emb ps`
and 14.5 MB of Kubernetes ESM.** That edge is Phase 3, which is consequently
promoted to the highest-value item on this list.

**Risk:** none. Verified: `npm run test:unit` 678/678 pass, build clean.

### Phase 2 — Lazy Docker client — DONE

`docker: new Dockerode()` is gone from `BaseCommand.init()`. `EmbContext.docker`
is optional and `src/docker/client.ts` exposes `getDockerClient()`, mirroring
Phase 3.

`dockerode` is CommonJS, so `createRequire(import.meta.url)('dockerode')` keeps
the accessor **synchronous** — no `await`, and the 17 call sites changed shape
only (`this.context.docker.x` → `getDockerClient().x`).

**Deviation from the original design.** The plan was a memoising getter on the
context object, which would have needed no call-site changes at all. That is a
trap: `BaseCommand.init()` does `setContext({ ...partialContext, monorepo })`,
and a spread *invokes* getters — silently reintroducing the eager load. Any
`{...context}` anywhere in the codebase would do the same. An explicit accessor
cannot be defeated that way, and it matches Phase 3.

`dockerode` brings `ssh2` (592 KB) and `@grpc/grpc-js` (652 KB) with it for
transports emb never uses, so all three leave together:
**1171 → 1004 modules, 5.30 MB → 3.53 MB, `emb ps` 1125 → 1046 ms.**

Two type fixes fell out: `retagIfNecessary`/`pushImage` took
`ReturnType<typeof getContext>['docker']`, which became nullable — now typed
`Docker` directly; and five specs that read `context.docker.x` needed `!`,
matching existing test style.

**Verified:** 678/678 unit, integration-features 26 passed, `emb images` and
`emb containers` both work against the real daemon.

### Phase 3 — Lazy Kubernetes client — DONE

`createKubernetesClient()` is gone from `BaseCommand.init()`. `EmbContext.kubernetes`
is now optional and populated on first use.

**Deviation from the original design.** The plan was to move construction into
`KubernetesCommand.init()`. That does not cover `RunTasksOperation`'s
`kubernetes` executor, which runs under `tasks run` — an ordinary
`FlavoredCommand`. Instead `src/kubernetes/client.ts` exposes:

```ts
getKubernetesClient(): Promise<KubernetesClient>  // memoised on the context
createKubernetesClient(): Promise<KubernetesClient>  // always fresh
```

`getKubernetesClient()` returns `context.kubernetes` when already set, so a
client injected by a test or a plugin wins over building a real one. The seven
call sites that read `context.kubernetes` now `await` it; all were already in
async functions.

The import inside is dynamic. Note `require(esm)` *does* work for this package
on Node 22.22, which would have allowed a synchronous accessor and zero call-site
changes — but it only landed unflagged in Node 22.12 and `engines` allows
`>=22.0.0`, so it would break users on 22.0–22.11.

Type-only imports of the SDK (`V1Pod`, `V1Status`) were made explicit with
`import type` so they cannot silently re-enter the runtime graph.

**Alone, this changed nothing** — 2116 modules before and after. A second route
was still live, which the single-path import tracer had hidden by only reporting
the shortest path. Cutting one of two edges to a package cuts nothing.

### Phase 4 — Dynamic import of k8s operations in `RunTasksOperation` — DONE

```ts
- import { GetComponentPodOperation, PodExecOperation } from '@/kubernetes/operations/index.js';
+ // inside runKubernetes():
+ const { GetComponentPodOperation, PodExecOperation } = await import('@/kubernetes/operations/index.js');
```

This was the second edge. **Together with Phase 3 it removes
`@kubernetes/client-node` from the `emb ps` graph entirely: 2116 → 1171 modules,
21.20 MB → 5.30 MB, and `emb ps` 1683 → 1125 ms.**

Lesson for the remaining phases: verify with `bench:modules`, not with a path
trace. A package is only gone when *every* edge to it is cut.

#### Test-suite side effect

`tests/setup/set.context.ts` built a real Kubernetes client purely to give
`vi.mockObject` a shape. Once the import became dynamic that cost 337 ms per
call, which pushed 19 tests past their 5 s timeout. The client is now simply
left undefined — every test that exercises Kubernetes already injects its own
mock. The unit suite went from 39 s to 21 s as a result.

### Phase 5 — De-barrel `BaseCommand` and `DockerImageResource`

These two are the welds that make everything else reachable:

- `BaseCommand` imports `DockerComposeClient` + context helpers from `@`
  → import from `@/docker/compose/client.js` and `@/context.js` directly.
- `DockerImageResource` imports `ResourceInfo, SentinelFileBasedBuilder` from
  `@/monorepo` → import from the concrete modules.

**Risk:** low-medium — import reordering can surface latent cycles (see below).
**Measured:** Phases 4+5 together, −347 ms (prototype).

### Phase 6 — Replace `graphlib`

`graphlib` is unmaintained and its only value here is a toposort, for which we
pay all 194 files of `lodash`. The API surface actually used is tiny:
`Graph` (`setNode`, `setEdge`, `predecessors`), `alg.topsort`, `alg.findCycles`
— all in `src/monorepo/utils/graph.ts` (202 lines).

Replace with ~60 lines of local code (Kahn's algorithm for toposort, Tarjan for
cycle detection, which is what `CircularDependencyError` needs).

There is existing unit coverage to validate against:
`tests/unit/monorepo/utils/{graph,runGraph,findRunGraph}.spec.ts`.

**Risk:** medium — real logic, not just import plumbing. Mitigated by the tests.
**Estimated:** −150 to −200 ms (not yet prototyped).

### Phase 7 — Regression guard

Add a unit test asserting a **module budget**: `emb ps` must compile fewer than
N modules. Startup regressions are invisible in ordinary tests and creep back
the moment someone adds a convenient barrel import. A module count is stable
across machines in a way wall-clock timing is not.

## Also found

`dist/src/monorepo/index.js` cannot be imported on its own:

```
Cannot access 'SentinelFileBasedBuilder' before initialization
```

A circular dependency between `monorepo/index.js` and
`docker/resources/DockerImageResource.js`. It is latent today only because
something always imports the docker barrel first — reordering imports anywhere
could turn it into a hard crash. Phase 5 touches exactly these two files and
should resolve it; if not, it needs fixing on its own merits.

## Progress

All figures from klaro, `oclif.manifest.json` present, median of 3 batches x 6
runs. Noise band is ~150 ms.

| | baseline | Phase 1 | Phases 3+4 | Phase 2 |
| --- | --- | --- | --- | --- |
| node boot | 101 ms | 94 ms | 86 ms | 88 ms |
| `emb --version` | 199 ms | 191 ms | 195 ms | 204 ms |
| `emb tasks` | 1267 ms | 1263 ms | 922 ms | **883 ms** |
| **`emb ps`** | **1683 ms** | 1452 ms | 1125 ms | **1046 ms** |
| `docker compose ps` | 429 ms | 448 ms | 407 ms | 524 ms |
| modules for `emb ps` | 2116 / 21.20 MB | 2116 / 21.20 MB | 1171 / 5.30 MB | **1004 / 3.53 MB** |

**`emb ps` is down 38% (−637 ms) and parses 83% less JavaScript.**

Note `docker compose ps` drifted from 429 ms to 524 ms across these runs — the
machine is not identical between sessions. The module counts are the trustworthy
figures; wall-clock is directional.

The 231 ms Phase 1 drop remains **unattributed** — module counts were identical,
so nothing stopped being loaded, and it sat only just outside the noise band.

Remaining weight in `emb ps`, and which phase takes it:

| package | source | phase |
| --- | --- | --- |
| `zod` | 524 KB | needed (config validation) |
| `@oclif/core` | 280 KB | framework |
| `yaml` | 280 KB | needed (config parsing) |
| `protobufjs` | 255 KB | **5** — via `docker/index.js` → `docker/protobuf` |
| `execa` | 220 KB | needed (compose subprocess) |
| `ajv` | 201 KB | needed (schema validation) |
| `lodash` (via `graphlib`) | 144 KB | **6** |

Only ~400 KB of the remaining 3.53 MB is still removable by the planned phases.
The rest is genuinely used, which means Phases 5 and 6 are worth appreciably
less than Phases 2/3/4 were — worth re-scoping before starting them.

## Expected outcome

Prototyped on `examples/fullstack-app` by patching `dist/`:

| state | `emb ps` |
| --- | --- |
| baseline (linked checkout, no manifest) | 1666 ms |
| + manifest | 1408 ms |
| + Phases 4 & 5 | 1061 ms |
| + Phase 2 | 965 ms |

Phases 1–6 should land `emb ps` around **800 ms**, against a theoretical floor
of ~575 ms (100 node boot + 160 oclif + 60 emb init + 250 docker compose).

That is roughly **2x faster**, and the remaining time would be genuinely spent
on Docker rather than on parsing JavaScript.

## Out of scope

- The `docker compose ps` subprocess (~400 ms on klaro). Real work, and it is
  the floor for any wrapper around the compose CLI. Bypassing it via the Engine
  API is a separate design question with its own tradeoffs.
- oclif's own ~160 ms bootstrap. Framework cost; not worth fighting.
- Bundling `dist/` into a single file. It would help — most of the remaining
  cost is per-file `stat`/`open`/`resolve` — but it is a build-system change
  with debuggability and source-map consequences. Worth considering only if
  Phases 1–6 fall short of the target.
